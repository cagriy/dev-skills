# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A Claude Code **plugin** (`.claude-plugin/plugin.json`, manifest name `dev` — kept deliberately short because it namespaces every slash command, e.g. `/dev:feature-design`; the plugin is distributed as `dev-skills` via the `ai-tools` marketplace repo) that ships a TDD-driven feature workflow plus a few standalone helper skills under `skills/`. There is no build step — the artifact is mostly the SKILL.md content itself. A small test suite lives under `tests/` (uv-managed): `uv run pytest` runs free static cross-file consistency checks; `uv run pytest -m llm` additionally runs golden-fixture judge tests through the `claude` CLI (token cost, on demand). Changes ship as edits to the markdown skill definitions, the `templates/feature-tracker.html` template, and the one bit of executable code the plugin carries: the `hooks/` remote-readiness check.

The skills divide into these groups:

- **Feature chain** — `feature-storm`, `feature-design`, `feature-plan`, `feature-implement`, plus the internal `feature-resolve` they all delegate to for pathing and the internal `feature-mockup` that `feature-design` alone delegates to for mocking up a user-visible surface.
- **Reporting** — `feature-list`, a standalone read-only reporter over `features/` (open features by default, every feature with the single legal argument `all`). Not part of the chain: it never calls `feature-resolve` (which would create folders and seed trackers) and never calls `lessons-capture`.
- **Router** — `feature-dispatch`, a model-only skill (`user-invocable: false`) that watches user prompts for non-trivial feature work (≥ ~75 LOC heuristic), recommends the right entry into the feature chain (`/feature-storm` for vague/high-level, `/feature-design` for clearer-but-undesigned), and on selection hands over via the `Skill` tool. Stays silent when the prompt is small, is a bug, or the user already picked an entry skill.
- **Bug workflow** — `bug-submit` (file a triaged bug under `bugs/`) and `bug-fix` (diagnose, TDD-fix, and close one open bug), plus the internal `bug-tracker-render` they both delegate to for (re)generating `bugs/bugs-tracker.html`. These do not use `feature-resolve` and do not write under `features/`.
- **Reflection / improvement** — `lessons-capture` (internal, called as the final step of the feature-* skills and `bug-fix`; `bug-submit` deliberately does not call it) and `lessons-learn` (user-only, periodic).
- **Workspace** — `set-herdr-label`, a model-only (`user-invocable: false`) side-effect helper that labels the [herdr](https://github.com/cagriy/herdr) agent pane the session is running in. Called by each of the four chain skills — set to the caller's own slug in their Step 1, cleared with no argument at their final step — and invokable by the model directly for ad-hoc labelling; it calls nothing itself. Gates on `HERDR_ENV == "1"`, targets `$HERDR_PANE_ID`, and is silent on both success and skip. It is the only skill whose no-op path is the *common* one — outside a herdr terminal it does nothing at all — which is why it has no Step 0 gate and no chat output to suppress.
- **Run reporting** — `usage-report`, a model-only (`user-invocable: false`) internal helper that reports what a chain run cost. Called by each of the four chain skills twice: `start <slug>` in their Step 1 (beside the herdr label) opens the window, and `report <slug>, …` in their final step closes it — printing a `Run usage` markdown table, appending one JSONL line to `<config-dir>/dev-skills/usage/runs.jsonl`, and filling that stage's two tracker tokens. It holds no domain logic: every figure, the transcript schema and the tracker write live in `scripts/usage_report.py`, so a transcript-format change is a one-file fix. Takes its pathing as input and therefore **never calls `feature-resolve`**; **never calls `lessons-capture`**. A failure anywhere in reporting prints one `usage report skipped — …` line and never fails, blocks or slows the calling skill. `tests/test_static.py::TestUsageReportLifecycle` guards the call sites, the token ownership and the placement asymmetry below.
- **Diagrams** — two standalone renderers, each pairing one skill with one template under `templates/`, each writing a self-contained interactive HTML page and nothing else, neither calling `lessons-capture`. `diagram-update` renders `diagram/index.html` (this plugin's own end-to-end workflow) and **refuses outside this repo**; `diagram-c4-update` renders `diagram/c4.html` + `diagram/c4-model.json` (a C4 architecture model of whatever project it is run in) and **runs anywhere**. That scope difference is the reason they are two skills and two templates rather than one of each — see the group entry below.
- **Evals** — two standalone scorers, both read-only towards the repo, writing nothing under `features/` or `bugs/`, never calling `lessons-capture`. `evals-code-run` evaluates the branch's unpushed commits across four dimensions (duplication vs the rest of the repo, bloat, inefficiency, security), each as a 0–100% affected-lines score (higher is worse) plus a ≤100-word `feature-implement`-improvement recommendation, appending four entries per run to `~/.claude/evals/code.json`. `evals-e2e-run` evaluates a chain-implemented feature end-to-end — artefact quality (storm/design/plan) and stage-to-stage consistency (including implementation vs each artefact) — as up to eight 0–100 scores (higher is better), each sub-80 score carrying a ≤100-word recommendation for the responsible feature-* skill, appending one entry per eval run to `~/.claude/evals/design.json`. Both are offered by `/feature-implement`'s closing step (Step 11), which on consent runs them in two parallel read-only subagents — which is also why `evals-e2e-run` deliberately has no gate verifying the unpushed work "is" a feature.

## Terminology — "stage" vs "step"

Two words are overloaded across the skill files; the four feature-* `SKILL.md`s carry a mirrored "Terminology (plugin-wide)" note near their top, and this is its canonical source.

- **Step** — a numbered step of a *skill's own procedure* (the `## Step …` headings, e.g. *Step 4*). The only other legitimate use of "step" is the **TDD steps** inside a plan stage (write test → confirm fail → implement → confirm pass). In `feature-implement`, *Step 5*'s lettered sub-steps (`5a`–`5i`) are procedure steps that iterate over plan stages — don't conflate the two.
- **Stage** — two distinct senses. A **chain stage** is one of `storm → design → plan → implement`: it appears as `stage=<slug>` in the `feature-resolve` call, as `stage_file` (a skill's output `.md`), as `present_stages` in the resolver, and as the tracker's `data-stage`. A **plan stage** is a committable unit of work *inside* the implementation plan (`Stage 1`, `Stage 2`, …) — `/feature-plan` creates them and `/feature-implement` builds one per commit. The commit message `<type>(plan v<N>): Stage <M> —` uses both senses at once (`plan` = chain stage, `Stage <M>` = plan stage).

A procedure step is never a plan stage, and a plan stage is never a procedure step. When editing, keep the four mirrored skill-level notes aligned with this section.

## The skill chain (architecture)

```
                  (model-only, fires on feature-shaped prompts)
                              feature-dispatch
                                    │
                  ┌─────────────────┴─────────────────┐
                  ▼ (vague / high-level)              ▼ (clear-but-undesigned)
/feature-storm  →  /feature-design  →  /feature-plan  →  /feature-implement
       │                │                  │                   │
       │                ├─ feature-mockup (Step 5, UI surfaces only)
       │                │                  │                   │
       ├────────────────┴──────────────────┴───────────────────┤
       │     each one calls feature-resolve at the start       │
       │     (folder, version, stage_file, tracker_file)       │
       │                                                       │
       └─────── each one's final step calls lessons-capture ───┘
                            │
              ~/.claude/dev-skills/lessons/<slug>.md
                            ↑
       /dev:lessons-learn <slug> (user-invoked, periodic)
```

Per-feature output structure (in the **target project's** cwd):

```
features/
  feature-v<N>-<description>/
    feature-storm-v<N>-<description>.md       ← optional
    feature-design-v<N>-<description>.md
    feature-plan-v<N>-<description>.md
    feature-implement-v<N>-<description>.md   ← (future stage; not yet emitted by /feature-implement)
    feature-v<N>-tracker.html                 ← seeded by feature-resolve, updated by each stage
    mockups/                                  ← optional; written only by feature-mockup
      mockup-v<N>-<name>.html                 ← one per mockup / named alternative
```

- **`feature-dispatch`** — model-only router (`user-invocable: false`). Fires when the user's most recent message looks like non-trivial feature work (~75 LOC heuristic) and recommends the right entry into the feature chain: `/feature-storm` when the requirement is vague / under-specified at the product layer, `/feature-design` when the user is clear on what they want but the work still needs a real technical design. Asks once via `AskUserQuestion` with three explicit options (recommended skill first, alternative second, "Continue without dispatch" third) and on selection hands over via the `Skill` tool with the user's original request as the argument. Stays silent when the prompt is small, is a bug, the user already typed an entry slash command, or work is already in flight. Does not call `lessons-capture`. The chain-in is recognised by `feature-storm` and `feature-design` Step 0 (header `"Route this feature?"` + option label starting `"Run /feature-<slug>"`), which lets the dispatcher's confirmation stand in for theirs.
- **`feature-storm`** *(optional)* — high-level product/requirements brainstorm. Covers goals, scope, users, technical constraints, alternatives, risks, open questions. Writes a 7-section storm.md. Step 0 is the proactive-confirmation gate. **Step 3 is deliberately two-halved: 3a generates, 3b converges.** The skill must put ideas on the table the user did not bring (adjacent capabilities, alternative product approaches, smaller cuts, bigger frames, unconsidered users/scenarios, things to deliberately not build) and offer them for adoption — a round that only asks "what did you mean by X?" has under-delivered. Ideas are *offered, never assumed in*: adopted ones shape §2/§3, declined approaches land in §5, declined capabilities in §3's out-of-scope list, so a considered idea is never dropped without a trace. Step 3's exit condition is **100% scope certainty** — every capability discussed is either in this version or explicitly deferred by name; the only uncertainty allowed past the Step 4 gate is design-level (recorded in §7). An item still unsettled after three rounds is forced to an explicit in/out decision rather than carried into the design as a hedge. Don't reduce 3a back to a clarification-only interview, and don't let the summary hedge scope.
- **`feature-design`** — produces the technical design under `features/feature-v<N>-<desc>/feature-design-v<N>-<desc>.md`. Clarification loop (Step 4) and self-review (Step 7) are load-bearing — skipping them defeats the skill. **Step 4 is an interview that runs until the design is fully determined, not a fixed handful of questions.** It ends on a six-part *readiness test* — a dry-drafted §5 with no guesses, no hedge language ("TBD", "either … or", "as appropriate"), an §8 that would read "None — all decisions closed.", every storm §7 item closed, the two-engineer equivalence test met, and a round that surfaced nothing new — and never on a question count, elapsed rounds, or the user having already answered a few. Its coverage list is the checklist of what must be *resolved* (scope, acceptance criteria, per-requirement behaviour, approach choices, constraints, data and state, interfaces/integration, failure behaviour, scale and concurrency, permissions and trust boundaries, operability); each item is closed either by asking the user (their call: product behaviour, anything they'd notice, anything trading cost/risk/effort, anything irreversible, any genuine toss-up) or by a grounded decision recorded with rationale in §5/§6 — never by a guess, and never self-decided merely to save a round-trip. Don't reintroduce a question budget or soften the exit to "no remaining decision would change the design"; the asymmetry is deliberate (a padded round costs the user seconds, a guessed design costs a plan and an implementation). Step 5 delegates to `feature-mockup` and folds the returned `decisions` into §5, the rejected alternatives into §6, and a relative-path link to the accepted mockup into §5 and the tracker. Its **fire/skip decision (Step 5a) is a rule with four named exits, not a judgement call**: it fires only when the feature has a user-visible surface *and* that surface's appearance is not already settled, and skips on **No user-visible surface** / **Appearance already settled** (the user supplied a screenshot, image, wireframe, design-tool link, an existing page to copy, a field-by-field spec precise enough to implement, or a prior accepted mockup for the same surface — cite their artefact, don't draw over it) / **Mechanical delta** (one more field, column, row, label, or a value swap the user specified exactly) / **User declined**. The applied condition is recorded in chat and in §5, so a missing mockup is always a visible decision. "The UI seems obvious" is explicitly *not* a skip; genuine ambiguity folds one question into the Step 4 clarification round instead of costing a standalone round-trip. A *partially* supplied reference is a fire, not a skip — it goes through as `references=` for the mockup to extend. Two guards keep the rule from inverting on exactly the features that need it most — **Step 4 is carved out from closing appearance** (placement, hierarchy, density, which components carry it, type/colour treatment all route to Step 5, including visual items seeded from the storm's §7; Step 4 asks only the visual questions that *bound* the mockup, i.e. what feeds `kind=` and `references=`), and **5a opens with a one-way fire trip-wire** checked before any exit (a visual storm §7 item, or Step 4 having touched appearance at all, forces a fire and disables all four exits). Without them, more UI unknowns meant more Step 4 UI answers meant a stronger-looking *Appearance already settled* skip — the exact opposite of the intent. `Appearance already settled` therefore covers only material the user brought **independently of this skill's own clarification round**; an option they picked in a Step 4 `AskUserQuestion` never settles appearance. `tests/test_static.py::TestFeatureMockupContract` guards all three (carve-out, exclusion, trip-wire) plus Step 5's place in the load-bearing list. Can start cold (no storm) or pick up from a just-saved storm via Step 0 chain-in.
- **`feature-plan`** — produces `feature-plan-v<N>-<desc>.md` under the same feature folder. Refuses to run without an existing design; refuses if design §8 (Open questions) is non-empty. The plan file is named directly off the resolver — there is no separate plan-versioning. Split execution: Steps 0–2 and 11 run in the main agent (Step 0 gate; Step 1 resolver — where any overwrite/older-version questions get asked; Step 2 subagent launch + verification; Step 11 summary relay + chain offer into `/feature-implement`), while Steps 3–10 (design read → grounding → draft → decision protocol → review → tracker → lessons → summary) run inside a **single general-purpose subagent** briefed with the resolver block plus the verbatim step text. The subagent never prompts the user: planning-level gaps (stage ordering, flags, harness, file paths) are decided autonomously and recorded in the plan's *Planning decisions taken* section (surfaced in the summary), while design-level gaps or a non-empty design §8 make it halt with a `BLOCKED:` final message the main agent relays verbatim (skipping Step 11). On success the subagent's final message is exactly the Step 10 summary block, which the main agent relays unmodified.
- **`feature-implement`** — executes the plan stage-by-stage on the **current branch**. Never creates branches, never pushes, one commit per green stage. Resumes from the last committed stage by `git log --grep`. Detects project tooling (`TEST`/`LINT`/`FORMAT_CHECK`/`TYPE_CHECK`/`BUILD`) from manifests + CI config and reuses those slot names throughout. Establishes a test/lint baseline in Step 3 so pre-existing failures aren't gated as regressions. Step 3 also gates on that baseline: if the `TEST` run is already red before any implementation, the skill halts (sub-point 9) and asks the user via `AskUserQuestion` to investigate now, file a bug (handover to `/bug-submit`), or stop — it never builds on a red suite, even under autonomous instructions (a truly headless run defaults to halting). The lint/type baseline does not gate this way; it stays an exclusion set. Step 5 opens by resolving an **execution strategy by rule — never by `AskUserQuestion`, never by model preference**: **Chunked** (one general-purpose subagent per consecutive `min(3, R)` stages) is the default, and **Direct** (every stage in the main agent) applies only on an explicit user request, at `R ≤ 2`, or when the pre-scan leaves ≤1 delegatable stage. Both are **sequential** (never parallel) and commit one-per-stage. The resolved strategy is announced in one line carrying `R` and the partition — the run's only checkpoint between Step 0 and code landing. A unit that hit a deviation, a Step 6 stop, or failed verification shrinks the *next* unit to one stage; a clean unit returns it to `min(3, remaining)`. The per-stage-only carve-out (live UI/browser verification, main-conversation-only tools, network provisioning) pulls individual stages back into the main agent at their ordinal position — it never forces the whole run Direct. The three-option question this replaced was answered the same way in 83% of 30 recorded runs and dismissed in 8, so it cost a round-trip and bought nothing; free model discretion is equally wrong, because the cheap path under an autonomous instruction is Direct. Subagents run the identical `5a`–`5i` cycle under a self-contained contract (plan/design paths, tooling slots, Step 3 baseline, exact commit format, git constraints, stop conditions) and obey every git rule; the main agent verifies each unit's commits landed before launching the next. Only Step 5's loop is ever delegated — Steps 7–11 (final coverage, tracker, lessons, summary, eval offer) always run in the main agent. Step 11 closes the run by asking (`AskUserQuestion`) whether to run the eval suite: on consent it launches `evals-code-run` and `evals-e2e-run` in **two parallel read-only subagents** (safe — different log files), each briefed to invoke its skill via the `Skill` tool with the user's confirmation carried in the brief, and relays their score summaries; declining, a headless run, or an eval failure never fails the implementation run.
- **`feature-resolve`** — internal-only (`user-invocable: false`). Called at the start of every feature-* skill with `stage=<slug>[, version=<N>][, description=<phrase>]`. Computes the correct `features/feature-v<N>-<desc>/` folder, creates it on first use, seeds `feature-v<N>-tracker.html` from the plugin template, and returns a parseable resolution block (`mode`, `version`, `description`, `feature_folder`, `stage_file`, `tracker_file`, `prereq_file`, `notes`). Never creates or edits stage `.md` files. Decides create-new vs continue-existing based on whether the latest folder already has the requested stage's file — with one guard on Rule C: a *missing* stage file means "skipped", not "pending", when the latest folder holds a **later** stage's file (or holds no stage file and no tracker, against a differing description), so `storm`/`design` fall through to create-new without asking. Without it, every storm following a design-first feature paid a confirmation round-trip with only one sensible answer.
- **`feature-mockup`** — internal-only (`user-invocable: false`, model-invocable), called by `feature-design` Step 5 with `feature_folder=`, `version=`, `feature=`, an optional `kind=<new|modify>`, and an optional semicolon-separated `references=` carrying user-supplied visual references. Those references are read first, **outrank** the grounded design-language digest on any visual choice they settle, and bound the alternatives offered — the caller skips this skill outright when the user's artefact or description already specifies the whole surface, so references arriving here are partial by construction. Shows the user what the feature will *look* like before the design is written: grounds in the host project's existing design language (UI layer, design tokens/theme, prior mockups in sibling feature folders), classifies the work as a **new surface** or a **modification**, then writes self-contained, offline, static HTML pages under `<feature_folder>/mockups/`. A new surface gets **one overall view** (`mockup-v<N>-overview.html`, screens + states + how it slots into existing navigation) presented for the user's opinion; a modification gets **2–4 uniquely named alternatives** (one file each, each rendering the existing surface plus the change, each differing on a real axis) for the user to choose between or redirect. Iterates via `AskUserQuestion` until the user accepts one — revisions overwrite the same file, new directions get new names, three non-converging rounds force an explicit settle/hand-back/drop decision — then marks the accepted file `Accepted <date>`, keeps every rejected alternative as the record of what was considered, and emits a parseable result block (`status`, `kind`, `mockup_dir`, `chosen_mockup`, `alternatives`, `design_language`, `decisions`, `open_ui_questions`, `notes`). `decisions` is the payload the caller designs against. Takes its pathing as input and therefore **never calls `feature-resolve`**; **never calls `lessons-capture`** (the reflection belongs to `feature-design`'s own lessons step) — it holds no `Skill` tool at all, so both are structurally impossible. Writes nothing outside `<feature_folder>/mockups/`, never application code, and never wires a mockup into the project. `status: not-applicable` (no user-visible surface) and `status: declined` both continue the caller's run rather than blocking it. Has no Step 0 confirmation gate — the caller already gated the run. `tests/test_static.py::TestFeatureMockupContract` guards the input slots, the result-block keys, both sides of the caller contract, and the model-only / no-`Skill` frontmatter.
- **`feature-list`** — standalone reporter over `features/` (not part of the chain, writes nothing). Takes **one optional argument whose only legal value is `all`**: with no argument it lists the **open** features (implementation not complete); with `all` it lists every feature. Anything else stops the skill with a one-line usage error — never a best-effort guess. Renders a single markdown table in **reverse date order** (newest activity first, ties broken on version descending) with one column per chain stage plus last activity and the next slash command to run. Per-stage status comes from the tracker's `data-stage`/`data-state` attributes corroborated by the stage `.md` files; because `/feature-implement` emits no stage file, implement completion comes from the tracker alone and *in-progress* implementation is detected from `(plan v<N>): Stage <M>` commits on the current branch. Dates come from the tracker panels' `Updated <YYYY-MM-DD HH:MM UTC>` chips, falling back to the last commit touching the folder, then file mtime, then `unknown`. Locates feature folders by read-only globbing and **deliberately not via `feature-resolve`** (same reason as `evals-e2e-run`: the resolver creates folders and seeds trackers). Does not call `lessons-capture`, and deliberately has **no Step 0 confirmation gate** — it writes nothing and spends nothing, so a gate would cost a round-trip and buy nothing; the Step 0 invariant below applies to the four chain skills, not to this reporter.
- **`bug-submit`** — standalone (not part of the feature chain). Files a bug report as a local folder under `bugs/` in the current repo for a bug the user just hit, optionally with image attachments copied into the bug folder, and writes a `bug-N-<desc>.md` report whose triage section is grounded in a quick read of the codebase. Allocates the next bug number by scanning both `bugs/` and `bugs/archive/`. Step 8 delegates to `bug-tracker-render` to (re)generate `bugs/bugs-tracker.html`. Writes only to the local filesystem — no GitHub issue, no gist, no push/commit. Step 0 is the proactive-confirmation gate; Step 3 is the mandatory clarification round. Unlike the other user-facing skills, `bug-submit` does **not** call `lessons-capture` — it's a simple filing skill and the reflection overhead isn't worth it.
- **`bug-fix`** — standalone (not part of the feature chain). Diagnoses, fixes, and closes **one** open bug. Selects the bug by number from `$ARGUMENTS` or the lowest-numbered open folder in `bugs/`; stops with a `/bug-submit` handover if none are open. Grounds in the codebase + last feature, clarifies via `AskUserQuestion`, then enforces a hard **root-cause gate** (Step 4 — evidence before any code change) and a **TDD cycle** (Step 6 — failing test first). Asks the user to verify when it can't test automatically (UI etc.), and loops back to diagnosis on failure. On confirmed resolution: appends a `## Resolution` section (incl. lessons learned) to the bug's `.md`, `mv`s the folder into `bugs/archive/`, calls `bug-tracker-render`, and makes **one commit on the current branch (never pushes)**. Step 1 is the proactive-confirmation gate (strict — it writes code + commits); Step 10 calls `lessons-capture` with the `bug-fix` slug.
- **`bug-tracker-render`** — internal-only (`user-invocable: false`). Called by `bug-submit` (Step 8) and `bug-fix` (Step 9) whenever the set of bugs on disk changes. Regenerates `bugs/bugs-tracker.html` wholesale from the shared template + the filesystem: sets `data-tracker-kind="bugs"`, blanks the feature panels, and renders one expandable Issues card per bug — open (`bugs/`) and closed (`bugs/archive/`), with relative-path screenshots. Holds no state; never touches bug folders or report `.md` files; degrades to a one-line skip note (rather than failing the caller) if the template is missing or we're not in a repo.
- **`evals-code-run`** — standalone (not part of the feature chain). Scores everything committed on the current branch but **not yet pushed** (`@{u}...HEAD`; an explicit base ref can be passed via `$ARGUMENTS` when there is no upstream) across four dimensions — **duplication** (checked against the rest of the repo, not just the diff), **bloat**, **inefficiency**, **security** — via four parallel read-only subagents with self-contained briefs. Each dimension yields `score = round(100 × affected added lines / total added lines)` (higher is worse; generated files/lockfiles excluded from the denominator) plus a ≤100-word language-agnostic recommendation for improving `feature-implement` (empty string when the score is 0). Appends exactly four entries — fields `repo_name`, `timestamp` (one shared UTC stamp per run), `eval-type`, `score`, `recommendation` — to the JSON array at `~/.claude/evals/code.json` (atomic temp-file replace; a corrupt log is moved aside to `code.json.corrupt-<ts>`, never silently discarded). Uncommitted working-tree changes are deliberately out of scope (the expected flow is that `feature-implement` commits each stage before evals run); zero unpushed commits means stop without writing. Read-only towards the repo — never commits or pushes; does not call `lessons-capture`. Step 0 is the proactive-confirmation gate.
- **`evals-e2e-run`** — standalone (not part of the feature chain). Scores a **chain-implemented feature end-to-end**: artefact quality and stage-to-stage consistency across storm → design → plan → implementation. Initiated by `/feature-implement`'s Step 11 eval offer (or typed directly), so it deliberately has **no gate** verifying the unpushed work "is" a feature — the initiator implies it; Step 0 is the standard proactive-confirmation gate. Resolves the feature version as the highest `v<N>` among `feature-implement` stage-format commits (`(plan v<N>): Stage <M>`) in the unpushed range (`@{u}..HEAD`; explicit base via `$ARGUMENTS`), falling back to the highest-versioned `features/feature-v<N>-*/` folder when there are none — located by read-only globbing, deliberately **not** via `feature-resolve`, which would create folders/seed trackers. Up to eight evals run as parallel subagents (inheriting the session model), each selected by input presence: `storm_quality`, `design_quality`, `plan_quality` (rubric-based), plus `design_consistency` (storm→design), `plan_consistency` (design→plan), `code_storm_consistency`, `code_design_consistency`, `code_plan_consistency` (implementation — the stage commits when present, else the whole unpushed diff — vs each artefact; all three skipped when there are no unpushed commits). Scores are `round(100 × items_met / items_assessed)`, **higher is better** (opposite polarity to `evals-code-run`); scores <80 carry a ≤100-word language-agnostic recommendation targeting the responsible skill (`feature-storm` / `feature-design` / `feature-plan` / `feature-implement`), ≥80 forces `""`. The main agent validates the result blocks and does a **single atomic append** — one entry per eval run, same five fields as `code.json` (`repo_name`, shared `timestamp`, `eval-type`, `score`, `recommendation`) — to `~/.claude/evals/design.json` (corrupt log moved aside to `design.json.corrupt-<ts>`); entry count varies per run, so consumers key on `eval-type`, never position. Read-only towards the repo; does not call `lessons-capture`.
- **`lessons-capture`** — internal-only (`user-invocable: false`). Called as the final step of the feature-* skills and `bug-fix` with the calling skill's slug (`bug-submit` is the one user-facing skill that does not call it). Appends one entry (or "no recommendation") to `~/.claude/dev-skills/lessons/<slug>.md` via a single atomic `>>` append. **Never edits any SKILL.md.**
- **`lessons-learn`** — user-only (`disable-model-invocation: true`). Consolidates the log for one slug, presents filtered improvements via `AskUserQuestion`, edits the target `SKILL.md`, then archives the entire active log as a UTC-stamped snapshot. Never auto-commits.
- **`set-herdr-label`** — model-only (`user-invocable: false`). Called by the four chain skills and directly by the model; it calls nothing itself (it holds no `Skill` tool, so `lessons-capture` is structurally unreachable — the `feature-mockup` precedent). Takes the desired label as its only argument and renames the herdr agent pane the session occupies, so parallel agents are distinguishable in the sidebar. **Skips silently unless `HERDR_ENV` is exactly `1`** — outside a herdr terminal the no-op is the normal path, which is why there is no Step 0 gate and no success message: it produces no chat output at all except one recoverable-error case. The target is always `$HERDR_PANE_ID` (the pane this session occupies); it must **never** be discovered via `herdr agent list` matched on `cwd`, because two sessions in the same repo collide and it would rename the wrong agent. herdr validates names server-side against `^[a-z][a-z0-9_-]{0,31}$`, so the skill normalises first (lowercase → collapse disallowed runs to `-` → strip to a leading letter → truncate 32 → strip trailing `-`/`_`). **An empty argument clears the label via `herdr agent rename <pane> --clear`** — that flag is the only mechanism that works, since herdr rejects both `""` and `"-"` with `invalid_agent_name`; a label that normalises to nothing takes the same path. Writes no files (holds neither `Write` nor `Edit`) and touches nothing in the workspace but the one pane. `tests/test_static.py::TestSetHerdrLabelContract` guards the gate, the env-var target, the `--clear` path, the charset documentation, and the model-only / no-`Skill` / no-write frontmatter.

- **`diagram-update`** — standalone renderer of `diagram/index.html`, this plugin's own workflow diagram. **Refuses outside this repo** (`jq -r .name .claude-plugin/plugin.json` must be `dev`). Re-derives everything from `skills/` and `hooks/` on every run and overwrites the page wholesale — it holds no state, so "create" and "update" are the same operation. Renders `templates/workflow-diagram.html` by substituting eight tokens; the template owns all presentation. Read-only except the one output file; never commits, never pushes; does not call `lessons-capture`.
- **`diagram-c4-update`** — standalone renderer of a **C4 architecture diagram** for whatever project it is run in: `diagram/c4-model.json` (source of truth) and `diagram/c4.html` (a self-contained, interactive page the reader drills down through, system context → containers → components). Renders `templates/c4-diagram.html` by substituting seven tokens. Three things distinguish it from its sibling and must not be "helpfully" aligned away: (1) it **runs in any repo** — Step 2 classifies the project as software / plugin-or-agent-asset / documents and that classification decides only *what to read*; (2) the model is **not purely re-derivable**, because system boundaries and the container-vs-component call are judgement, so the HTML is regenerated wholesale while the JSON is *reconciled* — recorded decisions and hand-tuned `col`/`row` survive, and unevidenced elements are retired rather than deleted; (3) it has a **bounded user-clarification round** (one `AskUserQuestion`, at most four questions from a closed catalogue, never a second round). Elements are placed on integer `(col, row)` cells whose pitch the template owns, so non-overlap is arithmetic rather than hope. Read-only except its two output files; never commits, never pushes; does not call `lessons-capture`.

The two diagram skills are **deliberately separate**, and their templates deliberately duplicate their design language and edge-drawing technique rather than sharing an extracted partial. Merging them was considered and rejected: one skill cannot both refuse-outside-this-repo and run-anywhere, and a shared template would ship the plugin-workflow engine (step badges, gates, subagent brackets, invocation pills — all dev-skills vocabulary) into every user's repo as dead code. There is also no build step here to share a partial through. They are meant to *look* like siblings, so restyling one is a prompt to consider the other. They link to each other through `{{WORKFLOW_C4_LINK}}` / `{{C4_WORKFLOW_LINK}}`, each resolved by a `test -f` against the other's output — so neither skill knows the other exists and both stay independently re-derivable. `tests/test_static.py::TestC4DiagramContract` guards the token contract in both directions, the grid geometry, the reciprocal links, and the "runs anywhere" property.

The reflection protocol lives in `lessons-capture` alone, the convention/version logic lives in `feature-resolve` alone, and the bug-tracker rendering lives in `bug-tracker-render` alone — in each case the callers used to (or would) inline the logic and drift, so it got extracted. Don't reintroduce inline reflection or inline `features/` scanning in the feature-* skills, and don't reintroduce inline tracker rendering in `bug-submit` / `bug-fix`.

## Non-negotiable invariants to preserve when editing skills

These are spread across the skill files but easy to break with a well-meaning edit:

- **Feature-* skill artefacts live under `features/feature-v<N>-<description>/`**, in the target project's cwd. Mockups are part of that rule: `feature-mockup` writes only into `<feature_folder>/mockups/`, never into the application's own template/asset/style tree, and never anywhere else. `docs/` is **legacy** — feature-* skills may read it for grounding context but never write to it. The lessons log under `~/.claude/dev-skills/` is the only feature-* output that lives outside the project. The bug-workflow skills do not write under `features/`. `bug-submit` writes its artefacts under `bugs/` in the target repo: a `bugs/bug-N-<description>/` folder per bug (report markdown plus copied-in images), and a regenerated `bugs/bugs-tracker.html` (via `bug-tracker-render`). `bug-fix` additionally modifies project source/test files (the fix), `mv`s a bug folder into `bugs/archive/`, and makes one commit on the current branch — it is the only skill in the plugin that commits, and it never pushes.
- **`feature-resolve` is the single source of pathing.** The four chain skills never glob `features/`, never increment versions themselves, and never construct stage file paths by string concatenation. They invoke `feature-resolve` and use its returned `feature_folder` / `stage_file` / `tracker_file` / `prereq_file` verbatim. The two read-only skills that only *observe* `features/` — `feature-list` and `evals-e2e-run` — glob it by hand on purpose: the resolver creates folders and seeds trackers, so routing a read-only report through it would mutate the repo. Neither may ever be switched to the resolver.
- **The resolver runs *inline*, and a successful resolution never ends the turn.** `Skill` loads `feature-resolve` (and `feature-mockup` / `lessons-capture` / `bug-tracker-render`) into the caller's own context — it is not a subagent, and nothing "returns" to a waiting caller; the only real delegation in the plugin is `feature-plan` Step 2's `Agent` call. "Caller" language in those helpers is architectural shorthand for "the same model, a few steps later". Never write a bare "stop" / "return to the caller" as an internal helper's terminal instruction on its success path: 5-series models take it literally and end the turn, which strands the run (observed as a seeded feature folder, an empty tracker, and no artefact until the user types "continue"). Each helper's success path says *do not end your turn* and names the caller's next step; each of the four callers mirrors that guard at the end of its resolver step, and `feature-design` mirrors it again at the end of its Step 5 mockup call. Keep both halves aligned.
- **Integer versions only.** `v1`, `v2`, `v10` — never `v1.0`, `v1.2`. Numeric compare on version (so `v10` > `v9`). No minor-version revisions of stage files — to revise, you re-run the stage on a new feature version (default) or pass an explicit `version=<N>` to overwrite (resolver asks).
- **Step 0 (proactive-invocation confirmation) gate.** Each feature-* skill checks for the literal `<command-name>/<slug></command-name>` tag, or a chained opt-in from the previous skill's final step, or (for `feature-storm` and `feature-design`) a chained opt-in from `/feature-dispatch` (header `"Route this feature?"` + option label starting `"Run /feature-<slug>"`). Otherwise it calls `AskUserQuestion` once before doing anything. For `feature-implement` this is strictly enforced because it writes code and commits.
- **The herdr label is set in Step 1 and cleared before the final step's offer.** Both placements are load-bearing and neither is arbitrary. The set belongs in **Step 1, not Step 0**: Step 0 is the confirmation gate, so labelling ahead of it strands a label on a run the user declined, which has no end to clear it. The clear belongs **before** the final step's `AskUserQuestion`, not after: on the chain-in branch the skill hands over through the `Skill` tool and never returns to the step, so a trailing clear would silently never run. Every early exit clears too — `feature-plan`'s `BLOCKED:` relay, `feature-implement`'s red-baseline halt and Step 6 stop conditions — backed by a catch-all constraint in all four skills, because the enumerated exits cannot cover every halt. Subagents (`feature-plan`'s planning core, `feature-implement`'s stage units) **never** touch the label; it belongs to the main agent for the whole run. `tests/test_static.py::TestHerdrLabelLifecycle` guards the placements, the catch-all, and the mirroring.
- **The usage window opens in Step 1 and closes in the final step — and where it closes is deliberately asymmetric.** `feature-storm`, `feature-design` and `feature-plan` report **before** their chain-offer `AskUserQuestion`, for exactly the reason the herdr-label clear sits there: on acceptance they hand over through the `Skill` tool and never return to the step, so a trailing report would silently never run. `feature-implement` reports **after** its eval relay, because its final question hands over to nothing and control returns on every branch — and only from that position do the eval subagents the user opted into fall inside the window being measured, which is why it passes `evals_included`. This reads as an inconsistency and invites a tidying edit; do not make it. Every early exit reports with `outcome=halted` (`feature-plan`'s `BLOCKED:` relay, `feature-implement`'s red-baseline halt and Step 6 stop conditions), backed by a catch-all constraint in all four skills. Subagents never open or close the window — it belongs to the main agent for the whole run, like the label. `tests/test_static.py::TestUsageReportLifecycle` fails if any of the three moves after its offer, or if `feature-implement` moves before its.
- **Clarification steps run even in auto / non-interactive mode.** The skills explicitly override "skip clarifying questions" instructions — closing material ambiguity is the whole point. Don't add a bypass. **One deliberate scope limit, in `feature-design` Step 4 only: the loop does not close *appearance*** — placement, hierarchy, density, which components carry the surface, type/colour treatment belong to Step 5's mockup, which settles them with a rendered page instead of prose options. Don't "helpfully" add UI-look questions back into Step 4; doing so re-arms the *Appearance already settled* skip against the very features that need the mockup. Bounding questions (platform/breakpoint, new-vs-modify, does the user have a reference) stay in Step 4 — they feed `kind=` and `references=`. **Deliberate exception: `/feature-plan` asks no clarifying questions at all** — its planning core (Steps 3–10) runs in a subagent with no user channel, so planning-level ambiguity is decided autonomously and recorded in the plan's *Planning decisions taken* section, and design-level ambiguity halts back to the main agent (`BLOCKED:`) pointing at `/feature-design`. Don't add clarification prompts back into the plan core, and don't extend this exception to the other skills.
- **Skills are deliberately language-agnostic.** `lessons-learn` filter #3 actively drops or rewrites language/framework-specific suggestions. When editing a skill, keep examples as illustrative lists across ecosystems, not as a single canonical command.
- **Tracker token substitution is defensive.** Each skill substitutes only tokens that are still literal `{{...}}` — never overwrites content placed by an earlier stage. Future-stage tokens get the empty placeholder (`<p class="empty">Not yet filled — pending /feature-<step>.</p>`) the first time the tracker is touched. **The eight usage tokens are the one deliberate exception**, and they are owned end-to-end by `usage-report`: `{{<STAGE>_USAGE_CHIP}}` and `{{<STAGE>_USAGE}}` for each of the four stages. Because they have exactly one writer, a re-run *replaces* its own stage's rendered content between the `<!-- usage:TOKEN -->…<!-- /usage:TOKEN -->` anchors rather than skipping it, and blanks any other stage's still-literal token to an *empty anchored region* — never to nothing, or the first stage to report would delete tokens the other three could then never fill. Substitution is confined to the rendered body: the template's opening doc comment legends every token by name, and writing an anchor into it closes that comment early and spills the legend onto the page.
- **Tracker progress bar is owned per stage.** Each skill flips its own `data-stage="<slug>" data-state="pending"` → `complete` as part of its tracker update step, only when the stage file is written / committed (or finalised — for `/feature-implement`, after all stages are green). There is no in-flight `current` state: a step is either grey (not done) or green (done). Never touch another skill's `data-stage` entry. Those attributes and the panels' `Updated <YYYY-MM-DD HH:MM UTC>` timestamp chips are also the machine-readable status/date source `feature-list` reports from — renaming either breaks the report, and `tests/test_static.py` guards the `data-stage` half.
- **The Issues region is NOT a `{{token}}` — don't "consolidate" it into one.** The bug tracker's Issues panel is a living list owned solely by `bug-submit`, regenerated wholesale each run between `<!-- ISSUES_AT/OPEN/CLOSED:START -->…:END -->` markers. It is deliberately a different mechanism from the one-shot feature-panel tokens. Never write those literal comment markers inside the template's doc-comment block (an inner `-->` closes the doc comment early and breaks the page). Open/closed status is derived from `bugs/` vs `bugs/archive/`, and the Open/Closed counts are computed by the template's JS at load — never hand-written.
- **No symlinks anywhere.** Per global convention; also enforced in the skills (including the template copy in `feature-resolve` Step 6).
- **`lessons-learn` archives by snapshotting the whole active log** (`mv` to `<slug>.archive-<UTC>.md`) — it does not write per-entry status tags into the archive. Deferred entries get written back to a fresh active log.

## Skill frontmatter contract

Each `SKILL.md` starts with YAML frontmatter. The fields that matter for behavior:

- `user-invocable: true|false` — gates whether the user can type `/<slug>`. `feature-resolve` and `lessons-capture` are `false`; `lessons-learn` uses `disable-model-invocation: true` so only the user can trigger it.
- `model` / `effort` — deliberately unset in every skill, so each runs on the user's current session model/effort (and skill-launched subagents inherit the same). Don't reintroduce hardcoded model or effort pins — in frontmatter or in subagent-launch instructions.
- `allowed-tools` — narrowly scoped per skill. `feature-implement` needs full `Bash`; the others use `Bash(ls *)`, `Bash(find *)`, `Bash(cp *)`, etc. `feature-resolve` adds `Bash(cp *)` for tracker seeding.
- `argument-hint` — shown in the slash-command picker.

## Files

- `skills/<slug>/SKILL.md` — the skill definitions; this is the product.
- `.claude-plugin/plugin.json` — plugin manifest.
- `templates/feature-tracker.html` — token-substitution HTML template (`{{FEATURE_VERSION}}`, `{{DESIGN_BULLETS}}`, etc.) plus a 4-step progress bar (`storm` → `design` → `plan` → `implement`) using `data-stage` / `data-state` attributes. `feature-resolve` copies this into each new feature folder; each feature-* skill substitutes its own tokens and flips its own progress step. The same template doubles as the **bug tracker**: it carries a 5th "Issues" tab and an optional `<body data-tracker-kind="bugs">` attribute that (via CSS) hides the stepper + feature tabs and shows only the Issues tab. The Issues panel is **not** `{{token}}`-driven — it is a living list regenerated wholesale by `/bug-submit` between HTML-comment markers (`<!-- ISSUES_OPEN/CLOSED/AT:START -->…:END -->`). Open vs. closed comes from `bugs/` vs. `bugs/archive/`; cards are expandable `<details>` with relative-path `<img>` screenshots. It also carries the eight usage tokens (`{{<STAGE>_USAGE_CHIP}}` / `{{<STAGE>_USAGE}}`), filled solely by `usage-report`. **The template has two consumers, not one** — `usage-report` fills the usage tokens and `bug-tracker-render` blanks all twenty feature-panel tokens by name — so adding or renaming a token is always a two-skill change. Forgetting the second consumer leaks literal `{{DESIGN_USAGE}}` text into every regenerated bug tracker.
- `templates/workflow-diagram.html` — presentation + interaction engine for `diagram/index.html`, rendered by `diagram-update` from eight tokens. Owns the card/step board, the skills-only overview, hover-revealed connectors, badges and pop-ups.
- `templates/c4-diagram.html` — presentation + interaction engine for the C4 page, rendered by `diagram-c4-update` from seven tokens. Owns the C4 shapes, the drill-down navigation (hash-routed, breadcrumbed), the derived boundary rectangles, the auto-generated legend, and **the grid geometry**: `--c4-box-w/h` and `--c4-col-pitch/row-pitch` CSS custom properties are the single source of truth for layout, read by the page's own JS and pinned against the SKILL.md by `tests/test_static.py`. Non-overlap is a theorem — one box per cell, pitch exceeds box size — and the boundary padding must fit the leftover gutter, which the test asserts arithmetically.
- `diagram/` — generated output, committed so GitHub Pages can serve it: `index.html` (workflow) and, once `/diagram-c4-update` has run here, `c4.html` + `c4-model.json`. Both pages are overwritten wholesale; never hand-edit them.
- `docs/` — hand-written research notes, not generated and not part of the product: `c4-model.md` (the C4 model — abstractions, diagram levels, notation rules, review checklist) and `c4-diagramming-tools.md` (tooling evaluation and the reasoning behind the hand-rolled renderer). `diagram-c4-update` cites both. Distinct from the **legacy** `docs/` convention mentioned under the feature-* invariants, which refers to a target project's own docs folder, not this one.
- `scripts/usage_report.py` — the plugin's **second** piece of executable code, alongside `hooks/remote-check.sh`. Stdlib-only Python (it is invoked as the system `python3`, not the project venv), importable as a module and runnable as a CLI (`start` / `report`). It is the only place that knows Claude Code's transcript schema: it locates the session transcript, windows it between the run's start marker and now, dedupes assistant entries by `requestId` (the transcript writes several snapshots per request, so without this every figure inflates), aggregates main and subagent usage separately, and renders the chat table, the tracker fragment and the log line. It writes only under `<config-dir>/dev-skills/usage/` and an explicitly passed `--tracker`; it makes no network calls and spawns no subprocesses. Unit-tested by `tests/test_usage_report.py` against synthetic JSONL fixtures. Its `main()` never raises and always exits 0 — any problem degrades to one `usage report skipped — …` line, so a reporting failure can never fail the calling skill.
- `hooks/hooks.json` — plugin-shipped hook config (auto-discovered; top-level `"hooks"` key, same schema as settings.json). Registers `hooks/remote-check.sh` on **SessionStart** and **UserPromptSubmit**, each passed a mode arg (`sessionstart` / `userprompt`) via `${CLAUDE_PLUGIN_ROOT}`.
- `hooks/remote-check.sh` — the only executable code in the plugin. A remote-readiness *warning* (not a gate): it `git fetch`es and, if the current branch is behind its upstream, emits both a user-visible `systemMessage` (a terminal warning, so the behind-state is never silent) **and** an `additionalContext` note instructing Claude to proactively **ask** the user via `AskUserQuestion` on its next reply whether to run `git pull --ff-only`. The hook itself never pulls and never prompts — hooks are non-interactive, so the ask can only come from Claude on a turn, and only once the user sends a message (there is no assistant turn at the blank session-start screen). The `systemMessage` is load-bearing: `additionalContext` alone is injected into Claude's context only and is *not* shown to the user, which is why the behind-state produced no visible feedback before. **SessionStart always fetches and resets the throttle; UserPromptSubmit fetches only when the last check is older than 2h** (state in `<git-dir>/dev-skills-remote-check`, never committed), so it never nags every prompt. No-op outside a git repo, with no upstream, or offline; it never pulls and never blocks. It is a complement to — not a replacement for — checking remote state at the point work happens; a once-or-throttled fetch can't see a remote that advances between checks, so it warns rather than enforces.
- `.gitignore` — ignores `.DS_Store` and a local `cli/` workspace.

## Editing workflow

Edits to a `SKILL.md` are usually applied via `/dev:lessons-learn <slug>` after the log accumulates signal — that path keeps changes traceable to captured runs. Manual edits are fine when fixing wording, fixing broken cross-references between skills (e.g. Step numbers in the chain, chain-in opt-in checks, tracker token names), or shipping a structural change that the lessons system can't drive.

When changing one feature-* skill, scan the other three for mirrored sections — the `feature-resolve` invocation block (including its closing inline-execution / do-not-end-your-turn guard), the chain-in opt-in checks in Step 0, the tracker update step, the lessons-capture call, the two `set-herdr-label` blocks (**Label the herdr pane** in Step 1, **Clear the herdr pane label** in the final step), and the two `usage-report` blocks (**Start the usage window** in Step 1, **Report the run usage** in the final step) all appear in all four. Keep them aligned; `tests/test_static.py::TestHerdrLabelLifecycle` fails on drift in the label blocks and `TestUsageReportLifecycle` on drift in the usage ones. The start blocks are mirrored verbatim modulo slug; the **report** blocks deliberately are not — `feature-implement`'s differs in both placement and arguments (see the placement invariant above).

When changing `feature-design` Step 5 or `feature-mockup`, keep the two sides of their contract aligned: the input slots (`feature_folder=`, `version=`, `feature=`, optional `kind=`) and the result-block keys must match on both sides, and both must keep the inline do-not-end-your-turn guard. `tests/test_static.py::TestFeatureMockupContract` fails on drift in either direction, and `evals-e2e-run`'s `design_quality` item 9 judges the mockup half of the design.

When changing `feature-storm`'s brainstorm document template or its section content rules, update `evals-e2e-run`'s `storm_quality` rubric in lockstep (and vice versa); the same producer↔judge contract holds between `feature-design`'s design document template / self-review rules and the `design_quality` rubric, and between `feature-plan`'s plan template / review rules and the `plan_quality` rubric. Judge and producer are written against each other, and the static test suite (`tests/test_static.py`) enforces the alignment half of all three contracts (§-numbers for storm/design, section names for plan).

When changing `templates/feature-tracker.html`, also scan the four feature-* skills **and** `bug-tracker-render` for any token name they substitute, plus `feature-list`, which *reads* the rendered result (the `data-stage` / `data-state` attributes and the `Updated …` timestamp chips) rather than substituting tokens. Adding a new token requires assigning ownership to exactly one skill; removing a token requires deleting the substitution step in whoever owned it. Two distinct fill mechanisms coexist in this one template, so keep them straight: the **feature panels** are one-shot `{{TOKEN}}` substitutions owned by the feature-* skills; the **Issues panel** is a marker-delimited region (`<!-- ISSUES_*:START/END -->`) regenerated wholesale by `bug-tracker-render`. If you rename a marker, the `data-tracker-kind` attribute, the `data-kind="issues"` tab, the `.issue*` CSS classes, or the issue-card HTML shape, update `bug-tracker-render` in lockstep — it is the sole consumer of the bug-tracker side of the template (`bug-submit` and `bug-fix` only call it).

When changing either diagram template, keep its token table in the owning SKILL.md in lockstep — `templates/workflow-diagram.html` ↔ `diagram-update` Step 5, `templates/c4-diagram.html` ↔ `diagram-c4-update` Step 8 — and remember that each carries a token pointing at the *other* page (`{{WORKFLOW_C4_LINK}}`, `{{C4_WORKFLOW_LINK}}`), so renaming one is a two-file change. Changing the C4 grid constants is a three-file change: the CSS custom properties, the numbers quoted in `diagram-c4-update` Step 7, and the geometry inequalities in `tests/test_static.py::TestC4DiagramContract` — which will fail loudly if the new gutter cannot fit the boundary chrome. The two templates are deliberate near-duplicates in their design language and edge drawing; when you restyle one, look at the other, but do **not** extract a shared partial (there is no build step, and the engines are diverging by design).

## Documentation — README and wiki

The GitHub wiki for this repo (its own git repository, `dev-skills.wiki`) is cloned locally at `../dev-skills.wiki`. The README is deliberately minimal — overview, the three principles, getting started, and links to the [live architecture diagram](https://cagriy.github.io/dev-skills/diagram/) (served by GitHub Pages from `main`; `.nojekyll` keeps files verbatim) and the wiki; all detailed documentation (getting started in depth, skills reference, architecture, bug workflow, evals & lessons, conventions, contributing) lives in the wiki pages.

When a change in this repo alters anything the README or wiki documents — skill behaviour, arguments, outputs, model/effort handling, conventions, repo layout — update the affected README and `../dev-skills.wiki` pages **in the same turn** as the change, not in a later pass. The static test suite cannot see the wiki, so this is the only mechanism keeping it honest. Wiki edits publish only when the wiki repo is committed and pushed (the usual don't-push-unasked rule applies; `/push` runs in whichever repo you invoke it from).
