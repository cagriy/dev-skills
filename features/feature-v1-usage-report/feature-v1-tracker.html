Highlights

  • Derives everything from Claude Code's own session transcripts — nothing new is instrumented.
  • Run boundaries come from explicit start/end markers keyed on session id + skill slug, never from inferring the invocation.
  • Compute lives in scripts/usage_report.py; a thin model-only usage-report skill is the documented entry point.
  • Main-agent and subagent usage are counted separately — the flat subagents/ directory means nested agents need no traversal.
  • Assistant entries are deduplicated by requestId; the transcript writes four snapshots per request, so skipping this inflates every figure fourfold.
  • Chat output is a markdown table with main / subagents / total columns, mirrored as an HTML table in this tracker.
  • Throughput is output tokens ÷ summed per-request time, computed once across main and subagents rather than per column.
  • Append-only JSONL log, so parallel herdr sessions finishing together cannot drop each other's entries.
  • Eight new tracker tokens owned solely by usage-report — and bug-tracker-render must blank twenty rather than twelve.
  • Reporting can never fail the calling skill: every error path is a one-line skip that still exits successfully.

Detail

Accepted mockup: grouped-columns — the chat table, the tracker table, and the throughput formula it was chosen with.

Summary

The four chain skills end without telling the user what the run cost. This feature adds a run usage report — elapsed time, active run time, a full token breakdown split between the main agent and its subagents, and output throughput — printed as a markdown table at the close of every chain-skill run, appended to a durable JSONL log, and mirrored into that stage's tracker panel.

Goals and non-goals

  • Goals: report time and the complete token breakdown at the close of all four chain skills; attribute delegated work correctly; persist runs so cost is comparable over time; surface the figures beside the artefact; never fail or slow the calling run.
  • Non-goals: currency cost estimates; skills outside the chain; per-request detail; backfilling historical runs; measuring the reporter's own cost.

Architecture

ComponentResponsibility
scripts/usage_report.pyThe compute engine and the only place that knows the transcript schema. Importable pure functions plus a main(argv) CLI.
skills/usage-report/SKILL.mdThin internal helper; parses arguments, runs the script, relays output. No domain logic.
Four chain SKILL.mdsTwo call sites each, mirroring the set-herdr-label blocks they sit beside.
templates/feature-tracker.htmlEight new tokens — a chip and a table per stage.
skills/bug-tracker-render/SKILL.mdSecond consumer of the shared template; must blank the new tokens too.
tests/Unit tests for the script, plus a static lifecycle test for the call sites.

Data model

A start marker at <config-dir>/dev-skills/usage/state/<session-id>-<slug>.json, keyed on session and slug so parallel sessions never collide. One JSONL line per run at <config-dir>/dev-skills/usage/runs.jsonl, carrying the split metrics plus outcome and evals_included.

Report placement is deliberately asymmetric

feature-storm, feature-design and feature-plan report before their chain-offer question, because on acceptance they hand over through the Skill tool and never return. feature-implement reports after its eval results are relayed, which is what places the eval subagents inside its measured window. A static test fails if any of the three moves after its offer.

Failure behaviour

Every failure path — missing session id, missing script, absent start marker, unreadable transcript, failed log write — prints at most one line and returns success. A missing start marker never causes a guessed start time: a fabricated window produces a plausible wrong number, which is worse than none.

Security

The transcript holds the full conversation; the script extracts only numeric usage, timestamps and identifiers. The log entry is built from an explicit field list rather than by filtering, and a unit test feeds a secret-shaped fixture string and asserts it reaches neither the log nor the table.

Testing

Unit tests per pure function against synthetic JSONL fixtures — dedupe, window boundaries, user-wait exclusion, malformed lines, depth-2 subagents, golden-string rendering, atomic interleaved appends. A TestUsageReportLifecycle static test guards the eight call sites, the asymmetric placement, the token ownership, and that the usage chip cannot be mistaken for feature-list's Updated chip.

Risks

  • The transcript schema is undocumented and could change on upgrade — confined to one file, with fixtures that fail loudly rather than reporting zeros.
  • Throughput's denominator includes prefill and network, so it is a response rate rather than pure decode speed — named and documented as such.
  • feature-implement's window includes evals, making runs non-comparable with eval-declined runs — recorded as evals_included so consumers can filter.
  • The asymmetric placement invites a "tidying" edit that would break the three chaining skills — stated in three places and asserted by test.

Rollout

Additive and unflagged. Order: the script's pure functions and their tests first, then its side-effecting half, then the template tokens together with the bug-tracker-render update, then the skill, then the four call sites (feature-storm first), then the static lifecycle test. Verification is a real chain run producing four tables, four log lines and four populated panels. Rollback is deletion.

Overview

The run usage report is built bottom-up in eight stages: the transcript-parsing engine first (the only part that can be wrong invisibly), then its two rendering surfaces, then its CLI and side effects, then the tracker template’s new tokens, then the usage-report skill, then the two halves of the call-site wiring across the four chain skills, and finally the documentation the change obliges. The order follows design §9’s rollout sequence — and Stage 4’s position ahead of Stage 5 is load-bearing rather than conventional, because the repo’s existing test_skill_tokens_exist_in_templates asserts that every {{TOKEN}} named in a SKILL.md exists in a template, so the tokens must land no later than the skill that names them.

Cross-cutting concerns

  • Security — the log dict is built from an explicit field list, never by copying and filtering an entry, and a secret-shaped fixture string is asserted absent from both outputs. The slug is validated before it can reach a filename, in the same stage as the first write. Stdlib only, no network, no subprocess — which is why repo_name comes from the start marker’s cwd rather than a git call.
  • Performance — entries stream line by line and are window-filtered before aggregation; subagent files are filtered by listing and mtime before parsing. Checked against a real multi-megabyte transcript in Stage 7.
  • Observability — each failure path prints exactly one usage report skipped — <cause> line, and the log’s outcome field separates completed from halted runs.
  • Compatibility — purely additive. Two bounded, self-correcting intermediate states are recorded: literal tokens in a tracker seeded between Stages 4 and 7, and an unconsumed start marker between Stages 6 and 7.

Planning decisions taken

Twelve decisions are recorded in full in the plan file. The most consequential:

  1. pythonpath = ["."] is added to the pytest config in Stage 1. Verified against the real runner: uv run pytest puts only <repo>/tests on sys.path, so import scripts.usage_report raises ModuleNotFoundError without it — the script’s unit tests cannot run at all until this lands.
  2. The script, not the skill, applies the tracker edits. The design says both in different sections; the Interfaces reading wins because requirement 10 needs a deterministic anchored replacement, which is unit-testable in Python and fragile as an LLM edit. The skill’s tool grant omits Edit so the split is structurally enforced.
  3. <config-dir> resolves as $CLAUDE_CONFIG_DIR falling back to ~/.claude. Verified: on this machine the config directory is an iCloud path, so hardcoding ~/.claude would find no transcript and write the log in the wrong place.
  4. Timestamps are parsed through a tolerant helper mapping a trailing Z to +00:00, because the repo declares requires-python = ">=3.10" and 3.10 rejects the exact form the transcript uses.
  5. A factual grounding error in the design was corrected in place: §5 placed the usage chip “inside the panel’s existing .chiprow”, but the template has no .chiprow — that wrapper exists only in the mockup. The chip now follows the panel’s <p class="section-timestamp">, which is already display: inline-block.

Deviations from plan

Nine, all recorded in the plan's Deviations from plan section. Two are substantive:

  • Blanking is anchored, not empty (Stage 3). Design §5 said the reporter blanks other stages' tokens "to the empty string". Taken literally, the first stage to report would delete the other three stages' tokens outright and they could never fill them afterwards, so a tracker would only ever show one stage's usage. They are blanked to an empty anchored region instead — renders as nothing, stays fillable.
  • Substitution is confined to the rendered body (Stage 7). Found by Stage 7's live integration check, which is the only place it could be found. The template opens with a doc comment legending every token by name; a whole-file substitution filled the legend too, and the --> in the anchors it wrote closed that comment about 80 lines early, spilling the legend onto the page as visible markup. Stage 3's unit tests could not catch it — they run against a minimal fixture with no legend, exactly the drift that stage's own risk note predicted. A new test class now pins the behaviour against the shipped template.

The other seven are minor API and test-scoping details.
